# 脚本编写技能

编写、调试、维护脚本（Python/Shell/Makefile/Tcl 等）的完整流程规范。

**触发条件**：用户要求编写、生成、调试或修改任何代码/脚本文件时激活。

## 1. 启动前检查

### 1.1 环境确认

- 脚本编写前先确认目标环境：运行时版本、可用工具链、包管理器权限
- 避免使用不兼容的语法或 API
- 示例：Python 3.8 不支持 `list[str]`，需用 `typing.List`

### 1.2 存放位置

- 脚本放 `$AI_script/<分类>/`，分类按语言/功能（python/bash/makefile/tcl 等）
- 目录不存在则先创建

## 2. 编码规范

### 2.1 结构要求

- 必须包含 `Main` 函数作为入口，负责参数解析和主流程调度
- 其他函数按单一职责切分，命名清晰

### 2.2 输入即契约

- 不硬编码可从输入推导的信息：列名从数据解析、列数自动统计、缺值数按实查决定
- 脚本服务于"此类数据"而非"当前这份数据"

#### 2.2.1 合并前验证

- 两表/多源合并前先比对数据量
- 不一致时定位差异并显式告知用户，不静默截断或补齐

### 2.3 输出格式约束

- 输出不仅内容须正确，格式的结构约束也必须满足
- Markdown 表格：分隔行 `---` 宽度 = 最大列宽 + 2（两侧空格）
- CSV：字段内含分隔符或换行时须正确转义
- JSON：键名唯一，特殊字符转义
- YAML：缩进层级正确，禁止 Tab/空格混用
- 其他格式依具体约束而定

### 2.4 内容感知对齐

- 表格列对齐方式由内容类型决定，通过采样自动检测
- 表头统一左对齐；数值右对齐，文本左对齐
- 检测策略：采样数据行，>50% 非占位值可解析为目标类型即判定

## 3. 调试流程

### 3.1 分步验证

- 复杂功能拆为独立步骤，每步实现后验证通过再进下一步
- 第一步产出（数据文件、中间脚本等）持久化保存
- 调试后续步骤时复用缓存结果，不重复执行已通过的步骤
- 仅输入条件变化时才重新执行

### 3.2 批量测试

- 批量测试前先用 1~2 组数据做单测验证
- 随机测试数据生成一次即持久化，修复 bug 时复用数据重跑而非重新生成
- 仅当数据不满足约束条件时才重新生成

### 3.3 测试中间文件管理

- 测试临时文件统一放在 `$Temp_Test/` 下
- **防串扰**：在 `$Temp_Test/` 下创建专属子目录（如 `$Temp_Test/<脚本名>_<时间戳>/`），避免多个终端同时写同一路径
- **用完即清**：测试完成后，需要归档的产物存入项目持久目录，其余连同子目录一并删除

#### 3.3.1 批量任务脚本归档

- 用于完成批量生成/转换/处理等任务的脚本，若具有复用价值（同类任务可能再次执行，仅参数不同），应归档到 `$AI_script/<分类>/` 下
- 归档后同步更新对应分类目录的 README.md
- 仅当脚本完全针对一次性场景、参数硬编码且无通用性时才可丢弃

## 5. 重复性任务

### 5.1 参数化优先

- 重复性任务（批量生成、批量补全、批量转换等）必须使用**参数化脚本**，接受命令行参数或函数参数控制输入/输出/配置
- 禁止手动逐个操作或使用硬编码一次性脚本

### 5.2 中间脚本测试

- 中间任务产生的脚本必须进行功能测试，开关由 `$Fun_Open` 中的 `TEST_INTERMEDIATE_SCRIPT` 控制（默认 `on`）
- 可信度要求由 `TEST_CONFIDENCE` 定义（默认 `90`%），可信度 = 通过用例数 / 总用例数
- 测试覆盖：正常输入、边界值、异常输入
- 未达标不可交付，先修复后重测

### 5.3 开关控制

- 是否测试、可信度阈值、是否归档均由 `$Fun_Open` 中的开关控制
- 执行前读取 `$Fun_Open` 获取当前值

## 4. 交付闭环

### 4.1 先验证再交付

- 脚本完成后必须用实际数据运行并检查输出，不可代码完成即视为交付
- 验证产物（测试脚本、中间数据）归档不丢弃

### 4.2 README 维护

- 脚本创建以"代码完成 + README 更新"为结束标志，不可先交付后补
- 更新已有 README 必须先 `read` 再 `edit` 追加，禁止 `write` 覆盖
- `write` 仅用于该目录下首次创建 README

### 4.3 自检

- write 新脚本后回复用户前必须自问：该分类目录的 README 是否已更新
- 答案为否则立即追加后才能回复

## 5. 性能优化

### 5.1 新建而非覆盖

- 对已有脚本进行性能优化时，**不直接覆盖原脚本**
- 新建文件，命名为 `<原脚本名>_perf.<扩展名>`（如 `find_sram_sv.sh` → `find_sram_sv_perf.sh`）
- 原因：保留原实现作为性能对比基线，便于后续验证和回退

### 5.2 README 必须记录性能对比

- 在对应分类目录的 README 中，同时列出原脚本和 `_perf` 脚本的条目
- `_perf` 条目的 **作用** 中必须写明：
  - 与原脚本实现方式的不同点
  - 为什么性能提升（算法/系统调用/数据结构层面的原因）
  - 性能对比数据表格（测试规模、原版耗时、优化版耗时、提升倍数）
